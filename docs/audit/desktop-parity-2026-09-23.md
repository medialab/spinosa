# Desktop parity map — 2026-09-24

This is a working-tree audit of the Electron desktop shell and React app against the TUI and Spinosa kernel, refreshed after `97dbd27d`. It maps user-facing flows and implementation owners; it is not a method-by-method SDK diff. “Missing” means no equivalent Desktop UI/flow was found in the reviewed paths, not that the kernel lacks the underlying capability.

## Architecture map

| Layer | Desktop implementation | TUI / kernel counterpart |
|---|---|---|
| Process startup and native bridge | `packages/desktop/src/main/index.ts`, `main/server.ts`, `main/ipc.ts`, `preload/index.ts`, `src/renderer/index.tsx` | CLI/TUI preflight and process startup in `packages/spinosa-kernel/src/cli/cmd/tui.ts`; direct terminal host in `packages/tui/src/app.tsx` |
| App shell, routes, persistence | `packages/app/src/app.tsx`; route pages under `packages/app/src/pages`; server and workspace persistence in `context/server.tsx` and `context/global.tsx` | Solid/OpenTUI route tree under `packages/tui/src/routes`; kernel state/config services under `packages/spinosa-kernel/src` |
| Server/API synchronization | `packages/app/src/context/server-sync.tsx`, `context/global-sync/bootstrap.ts`, `utils/server-compat.ts` | TUI reads the same kernel services through the SDK; API groups live under `packages/spinosa-kernel/src/server/routes` |
| Composer and slash/mention picker | `packages/app/src/components/prompt-input-v2.tsx`; shared UI and interaction state under `packages/session-ui/src/v2/components/prompt-input` | `packages/tui/src/component/prompt/index.tsx`, `prompt/autocomplete.tsx`; agent execution in kernel prompt/task services |
| Session, timeline, approvals | `packages/app/src/pages/session.tsx`, `pages/session/*`; permission/question docks under `pages/session/composer` | `packages/tui/src/routes/session/*`; kernel handlers under `session`, `tool`, `permission`, and `question` |
| Spinosa workspace lifecycle | `pages/home/spinosa-home.tsx`, first-launch code in `packages/desktop/src/renderer/onboarding.tsx` | `packages/tui/src/routes/home.tsx`, `component/dialog-spinosa-workspace-picker.tsx`, `packages/spinosa-kernel/src/cli/cmd/workspace-new.ts`, and shared create/onboard code in `packages/spinosa-core/src/commands` |

## Coverage and disposition

| Area | Desktop coverage | TUI/kernel comparison | Disposition |
|---|---|---|---|
| Launch, local sidecar, native OS features | Electron owns sidecar startup, credentials, file/directory pickers, deep links, updater, and menu actions. | TUI owns CLI preflight and terminal-native startup. | Platform-specific; not a UI parity gap. Keep the sidecar as the app’s only backend and do not restart it during local UI checks. |
| Home, recents, registry, and recovery | Spinosa home shows persisted recent opens and registered workspaces; the recovery dialog supports path recovery, identity scan/recovery, and unregister. | TUI enumerates the Spinosa workspace registry and handles available, missing, incomplete-import, and `cli_started` workspaces before launch. | Covered in `97dbd27d`: history survives opening/creating workspaces, externally registered workspaces are listed, and missing/incomplete entries can be recovered. The Desktop “New Workspace” onboarding flow is now kernel-backed; packaged-mode live verification remains separate. |
| Create/import workspace | The onboarding dialog selects source paths and workspace name, runs kernel onboarding, reports progress, supports cancellation/backgrounding, and offers launch/resume actions. | TUI `spinosa new <source>` and shared core onboarding create a workspace, copy the template, import/verify documents, record status, and prepare startup handoff. | Implemented in `97dbd27d` through the Desktop onboarding API; it is no longer a folder-picker-only flow. Keep the TUI/core workflow as the source of truth. |
| Startup brief | `/startup` is registered before a session exists; it reads `startup-prompt.md`, falls back to localized setup text, selects `build`, and submits. | TUI `/startup` uses the same startup prompt and build agent, but its setup-choice dialog can open the brief for review or open the workspace without submitting. `/init` is separate legacy behavior. | Prompt and agent are aligned. **Interaction difference:** Desktop currently submits immediately; TUI offers an explicit review/open choice. Decide whether Desktop should preserve that choice before auto-submit. |
| Slash commands and skills | Desktop loads kernel command `source` through both compatibility projections. The picker filters by query, groups all command handlers before skill files, labels both sections, and tags each row. | TUI’s slash command palette distinguishes command actions and skills through its own terminal list rendering. | Fixed. The section order also resolves collisions where a skill named `find`, `skills`, or `view` previously intercepted Enter before the app dialog command. |
| `@` agents and references | `@` lists non-hidden, non-primary agents as structured mentions; references, files, and MCP resources are separate mention kinds. Selecting an agent does not switch the primary agent. | The primary model receives the agent mention and may call the kernel `task` tool; permission checks still apply. `general` is a broad worker; `explore` is a restricted file-search worker with its own prompt. | Fixed for Spinosa workspace agents: when a project has both `.spinosa` and `.opencode`, the kernel now loads `.opencode/agents` as a compatibility mirror, then lets native `.spinosa/agents` definitions override it. This leaves the protected workspace template untouched. |
| Session and timeline | React timeline supports messages, tool activity, streaming reasoning, session actions, and child-session navigation. | TUI renders the same kernel session/tool state with terminal-specific layout and key navigation. | No concrete missing core action found in the reviewed paths. Different scrolling, focus, and terminal rendering are intentional platform adaptations. |
| Permissions and questions | Desktop docks expose allow-once, allow-always, reject, and question-response flows. | TUI exposes the same decisions and can render tool-specific context in its tool-detail and permission surfaces. | Core decisions are present. Tool-specific context parity needs a dedicated inventory; parallel Jev work in the current working tree is intentionally not treated as part of this committed audit. |
| Files, VCS, review, terminal | Desktop provides file tree, review/diff surfaces, embedded terminal, file picker, and shell actions. | TUI provides terminal autocomplete, shell mode, and terminal diff viewer. | Deliberate native interaction differences; no API-backed capability omission confirmed in the reviewed flows. |
| Providers, models, MCP, settings | Desktop provides provider/model selection and a full MCP manager with connect/auth flows. | TUI has provider/model/agent dialogs and MCP controls for configured servers. | Desktop is richer here; do not reduce it for visual symmetry. |
| Diagnostics, feedback, and observability | Desktop has status/report flows and split TUI/desktop/network log outputs in the current worktree. | TUI has terminal report/status actions and its own log streams. | The current worktree’s logging split and prior desktop feedback/branding updates are included in this map; no further gap confirmed in the reviewed paths. |
| Command palette search | Desktop palette searches commands, sessions, and files. | TUI palette lists reachable commands; sessions and file search have separate commands/autocomplete. | Search-scope difference, not a confirmed missing capability. Preserve unless user research favors a narrower palette. |
| Add/import files to an open workspace | No Desktop action or route equivalent was found in `packages/app/src`; onboarding imports during workspace creation/resume only. | The workspace prompt chip navigates to the `add-files` route, which runs the import/scan/type-selection workflow against an existing workspace. | **P1 confirmed gap:** users cannot invoke the TUI add-files flow after opening a workspace. Reuse the core import workflow and expose an in-workspace action; do not route users back through “New Workspace.” |
| Workspace visualizer | No corresponding Desktop route or visualizer surface was found in `packages/app/src`. | TUI has a dedicated visualizer route with Files/Flow/Activity views, graph inspection, session/file usage, coverage, and export. | **P2 confirmed gap:** the workspace visualization experience has no Desktop counterpart. Scope its data and interaction parity before porting the terminal canvas. |
| Update workspace framework/template | Desktop `/upgrade` updates the app/server binary; no workspace freshness check or template-update action was found in the app UI. | TUI workspace prompt chips check framework-version freshness and call the core `updateWorkspace` workflow. | **P2 confirmed gap:** updating Spinosa itself is not equivalent to updating an existing workspace’s framework/template files. Expose the shared core update workflow with a review/safety model. |
| Editor-selection file context | No equivalent `file_context_enabled` preference or toggle was found in Desktop prompt/editor paths. | TUI provides `app.toggle.file_context`; prompt submission can include or exclude the active editor selection. | **P2 candidate:** likely interaction gap, but confirm the intended Desktop editor-selection semantics before implementing; explicit file attachments/references are not the same behavior. |
| Background import monitoring | Desktop onboarding can background an import and the home list shows importing workspaces with a resume action; no persistent global progress chip/monitor was found. | TUI Home mounts a `BackgroundImportChip` and provides a monitor dialog. | **Partial parity:** work continues and can be resumed, but progress is less discoverable outside Home. Consider a persistent activity indicator/monitor. |
| Plugin routes and app slots | No TUI-style plugin route/slot mount was found in Desktop renderer paths. | TUI mounts plugin-provided routes and `app` / `app_bottom` slots. | **Conditional gap:** confirm whether Spinosa UI plugins are required to run cross-platform. If yes, define a Desktop-safe extension contract; terminal widgets cannot be mounted directly in React. |

## Coverage confirmed in `97dbd27d`

- Persisted and rendered recent workspaces, enumerated registry entries, and added recovery actions.
- Added the kernel-backed create/import/onboarding flow and progress/resume handling.
- Registered `/startup` before a session exists and retained the build agent/startup prompt behavior.
- Grouped and tagged slash commands and skills, and covered command-selection collisions.
- Preserved Spinosa project agent discovery when loading the compatibility `.opencode` mirror.
- Added sidecar, onboarding, HTTP, and product-log diagnostics; split TUI/Desktop/network log outputs.

## Remaining implementation boundary

Prioritize add-files-to-open-workspace first, then workspace visualization and framework/template updates. Startup review-before-submit and persistent background-import monitoring are UX parity decisions; file-context selection and plugin UI support need product confirmation. Terminal suspend, keyboard navigation, and terminal-specific rendering remain platform adaptations rather than gaps. This audit does not modify the protected `workspace-template` files or unrelated parallel-agent work.
